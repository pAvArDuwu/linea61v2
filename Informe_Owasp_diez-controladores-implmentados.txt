CAPÍTULO 2: V2 AUTENTICACIÓN (AUTHENTICATION)
--------------------------------------------------------------------------------
Control Oficial: Control V2.1.1 / V2.1.7 - Requisitos de Contraseñas de Mínimo 12 Caracteres

Vulnerabilidad y Riesgo:
El uso de contraseñas cortas o débiles (menores a 8-10 caracteres) expone las cuentas
de conductores y administradores a ataques de adivinación, fuerza bruta y diccionarios.
Severidad: ALTA.

Qué se implementó:
Se configuró globalmente la regla de contraseñas en Laravel exigiendo un mínimo obligatorio
de 12 caracteres para el registro de nuevos usuarios y el cambio de contraseña.

Archivos, Funciones y Líneas Modificadas:
- app/Providers/AppServiceProvider.php
  boot(): líneas 19-25. Define Password::defaults(fn() => Password::min(12)).
- app/Http/Controllers/Auth/RegisteredUserController.php
  store(): línea 36. Aplica Rules\Password::defaults() en el registro.
- app/Http/Controllers/Auth/PasswordController.php
  update(): línea 20. Aplica Password::defaults() en la actualización de perfil.

Código Implementado:
  public function boot(): void {
      Password::defaults(function () {
          return Password::min(12);
      });
  }

Procedimiento de Prueba en Vivo (Defensa):
1. Navegar a /register o ir a /profile.
2. Ingresar una contraseña corta (ej. "admin123").
3. Al enviar el formulario, el sistema bloquea el registro mostrando el error:
   "The password field must be at least 12 characters".
4. Ingresar una contraseña de 12 caracteres y se procesa correctamente.

CAPÍTULO 3: V3 GESTIÓN DE SESIONES (SESSION MANAGEMENT)
--------------------------------------------------------------------------------
Control Oficial: Control V3.2.1 - Regeneración de Identificador de Sesión (Anti-Session Fixation)

Vulnerabilidad y Riesgo:
Si un identificador de sesión no cambia antes y después de autenticarse, un atacante
que conozca la cookie previa puede secuestrar la sesión del usuario (Session Fixation).
Severidad: ALTA.

Qué se implementó:
Al iniciar sesión exitosamente, se ejecuta $request->session()->regenerate(). Al cerrar
sesión, se invalida la sesión activa y se regenera el token CSRF.

Archivos, Funciones y Líneas Modificadas:
- app/Http/Controllers/Auth/AuthenticatedSessionController.php
  store(): línea 29. Ejecuta session()->regenerate().
  destroy(): líneas 41-43. Ejecuta session()->invalidate() y session()->regenerateToken().
- config/session.php
  Líneas 30-35. Configuración de ciclo de vida de sesión.

Código Implementado:
  $request->authenticate();
  $request->session()->regenerate();

Procedimiento de Prueba en Vivo (Defensa):
1. Abrir el navegador e ingresar a la consola de desarrollo (F12 -> Application -> Cookies).
2. Observar el valor de la cookie "laravel_session" en la pantalla de login.
3. Iniciar sesión: verificar que el valor de la cookie cambia inmediatamente a un nuevo identificador.
4. Dar click en "Cerrar sesión": la cookie anterior queda revocada e invalidada en el servidor.

CAPÍTULO 4: V4 CONTROL DE ACCESO (ACCESS CONTROL)
--------------------------------------------------------------------------------
Control Oficial: Control V4.1.1 / V4.3.1 - Mínimo Privilegio y Separación de Roles (RBAC)

Vulnerabilidad y Riesgo:
Usuarios autenticados podían acceder a rutas administrativas o autoasignarse turnos
si las rutas no estaban restringidas estrictamente por rol en el servidor.
Severidad: CRÍTICA.

Qué se implementó:
Se agruparon las rutas web y API mediante middlewares de Spatie (role:admin,
role:admin|fiscalizador, role:admin|fiscalizador|dueño). Un conductor NO tiene acceso
a la asignación de turnos ni a los catálogos administrativos.

Archivos, Funciones y Líneas Modificadas:
- routes/web.php
  Líneas 29-54: Grupos protegidos con role:admin|fiscalizador, role:admin y role:admin|fiscalizador|dueño.
- routes/api.php
  Líneas 22-31: Grupo role:admin para endpoints de gestión operativa.
- tests/Feature/Api/ConductorCrudTest.php
  Líneas 58-65: Prueba automática assertForbidden() para no administradores.

Código Implementado:
  Route::middleware('role:admin|fiscalizador')->group(function () {
      Route::resource('asignacion-turno', AsignacionTurnoController::class);
  });
  Route::middleware('role:admin')->group(function () {
      Route::resource('users', UserController::class);
      Route::resource('roles', RolesController::class);
  });

Procedimiento de Prueba en Vivo (Defensa):
1. Iniciar sesión con un usuario con rol de "conductor".
2. Intentar ingresar manualmente a la URL http://127.0.0.1:8000/users o /asignacion-turno.
3. El sistema responde con la pantalla oficial HTTP 403 Forbidden.
4. Iniciar sesión como "admin": se tiene acceso total a todos los módulos.

CAPÍTULO 5: V5 VALIDACIÓN, SANITIZACIÓN Y CODIFICACIÓN
--------------------------------------------------------------------------------
Control Oficial: Control V5.1.1 - Validación de Entradas del Lado Servidor

Vulnerabilidad y Riesgo:
Si el sistema confía únicamente en JavaScript, un usuario puede omitir la selección
del mapa, alterar campos ocultos desde el navegador o enviar coordenadas inválidas.
Esto permitiría guardar paradas sin ubicación real o con datos geográficos corruptos.
Severidad: ALTA.

Qué se implementó:
El módulo de paradas usa Leaflet y geocodificación inversa con Nominatim para que el
usuario seleccione una ubicación en el mapa. Ese JavaScript rellena automáticamente el
nombre sugerido y los campos ocultos latitud/longitud. Como control de seguridad, Laravel
vuelve a validar esos datos en el servidor antes de guardar: nombre obligatorio,
coordenadas numéricas dentro del rango geográfico válido y estado limitado a valores
permitidos.

Archivos, Funciones y Líneas Modificadas:
- app/Http/Controllers/ParadaController.php
  store(): valida nombre, referencia, latitud, longitud y estado antes de guardar.
  update(): aplica las mismas reglas antes de modificar una parada existente.
- resources/views/parada/form.blade.php
  Usa Leaflet y Nominatim para seleccionar la ubicación y rellenar latitud/longitud.

Código Implementado:
  $request->validate([
      'nombre' => ['required', 'string', 'max:100'],
      'referencia' => 'nullable|string|max:255',
      'latitud' => 'required|numeric|between:-90,90',
      'longitud' => 'required|numeric|between:-180,180',
      'estado' => 'required|in:activo,inactivo',
  ]);

Procedimiento de Prueba en Vivo (Defensa):
1. Iniciar sesión como administrador.
2. Ir al módulo Paradas y presionar "Crear".
3. Escribir un nombre, pero NO seleccionar ningún punto en el mapa.
4. Enviar el formulario.
5. El sistema no guarda porque latitud y longitud son obligatorias.
6. Luego seleccionar una ubicación en el mapa: el JavaScript completa latitud/longitud
   mediante Leaflet y geocodificación inversa.
7. Enviar nuevamente y comprobar que la parada se guarda correctamente.

Prueba adicional para explicar seguridad:
- Aunque los campos latitud/longitud están ocultos, se pueden alterar desde DevTools.
- Si se cambia latitud a 120 o longitud a 200, Laravel rechaza el registro porque
  están fuera del rango permitido.

CAPÍTULO 6: V6 CRIPTOGRAFÍA ALMACENADA (STORED CRYPTOGRAPHY)
--------------------------------------------------------------------------------
Control Oficial: Control V6.2.1 - Hashing Robusto de Contraseñas con Sal (Bcrypt)

Vulnerabilidad y Riesgo:
Almacenar contraseñas en texto plano o con algoritmos vulnerables (MD5, SHA1) permite
la extracción masiva de credenciales en caso de fuga o acceso no autorizado a la BD.
Severidad: CRÍTICA.

Qué se implementó:
Se configuró el modelo User con el cast 'password' => 'hashed', asegurando que toda
contraseña se procese con el algoritmo Bcrypt y salt criptográfico automático con costo 12.

Archivos, Funciones y Líneas Modificadas:
- app/Models/User.php
  Líneas 27-28: Cast 'password' => 'hashed'.
- config/hashing.php
  Driver por defecto 'bcrypt' con factor de costo 12.

Código Implementado:
  protected function casts(): array {
      return [
          'password' => 'hashed',
      ];
  }

Procedimiento de Prueba en Vivo (Defensa):
1. Abrir phpMyAdmin o ejecutar en terminal: php artisan tinker.
2. Ejecutar: App\Models\User::first()->password;
3. Demostrar al jurado que el valor almacenado es un hash del tipo $2y$12$...

CAPÍTULO 7: V7 MANEJO DE ERRORES Y REGISTRO (ERROR HANDLING & LOGGING)
--------------------------------------------------------------------------------
Control Oficial: Control V7.1.1 / V7.1.2 - Respuestas de Error Limpias sin Fuga de Información

Vulnerabilidad y Riesgo:
La exposición de trazas de excepción (stack traces), rutas de Windows o consultas SQL
proporciona información crítica a atacantes para planificar vulnerabilidades.
Severidad: MEDIA.

Qué se implementó:
Se crearon vistas de error personalizadas y minimalistas en resources/views/errors/
que presentan mensajes amigables al usuario sin fugar información del servidor.

Archivos, Funciones y Líneas Modificadas:
- resources/views/errors/403.blade.php: Vista personalizada de acceso prohibido.
- resources/views/errors/404.blade.php: Vista personalizada de recurso no encontrado.
- resources/views/errors/500.blade.php: Vista personalizada de error interno.

Código Implementado:
  @extends('errors::minimal')
  @section('title', __('Forbidden'))
  @section('code', '403')
  @section('message', 'Acceso no autorizado al recurso solicitado.')

Procedimiento de Prueba en Vivo (Defensa):
1. Ingresar en el navegador a una URL inexistente: http://127.0.0.1:8000/ruta-inexistente-123.
2. Verificar que el sistema muestra una pantalla limpia de error 404 sin exponer rutas de Laragon ni código fuente.

CAPÍTULO 8: V8 PROTECCIÓN DE DATOS (DATA PROTECTION)
--------------------------------------------------------------------------------
Control Oficial: Control V8.2.1 - Ocultamiento de Secretos en Serializaciones JSON / API

Vulnerabilidad y Riesgo:
Exponer hashes de contraseñas o tokens de sesión en respuestas de la API permite que
clientes o intermediarios capturen datos confidenciales.
Severidad: ALTA.

Qué se implementó:
En el modelo User se declaró el atributo #[Hidden(['password', 'remember_token'])],
evitando que estos campos se serialicen al convertir el modelo a JSON o array.

Archivos, Funciones y Líneas Modificadas:
- app/Models/User.php
  Línea 17: #[Hidden(['password', 'remember_token'])].
- app/Http/Controllers/Api/AuthController.php
  Líneas 23 y 29: Métodos login() y me().

Código Implementado:
  #[Hidden(['password', 'remember_token'])]
  class User extends Authenticatable implements MustVerifyEmail { ... }

Procedimiento de Prueba en Vivo (Defensa):
1. Hacer una petición GET a /api/me enviando un Bearer token en Postman o navegador.
2. Inspeccionar la respuesta JSON devuelta: contiene id, name, email y roles, pero
   el campo password jamás está presente.

CAPÍTULO 9: V9 COMUNICACIONES (COMMUNICATIONS)
--------------------------------------------------------------------------------
Control Oficial: Control V9.1.2 - Banderas de Seguridad HttpOnly y SameSite en Cookies

Vulnerabilidad y Riesgo:
Cookies de sesión sin HttpOnly pueden ser leídas por código JavaScript malicioso en
el navegador, permitiendo el secuestro de la cuenta. Sin SameSite, se exponen a CSRF.
Severidad: ALTA.

Qué se implementó:
En config/session.php se fijaron http_only => true y same_site => 'lax'.

Archivos, Funciones y Líneas Modificadas:
- config/session.php
  Línea 172: 'secure' => env('SESSION_SECURE_COOKIE', env('APP_ENV') === 'production')
  Línea 185: 'http_only' => env('SESSION_HTTP_ONLY', true)
  Línea 202: 'same_site' => env('SESSION_SAME_SITE', 'lax')

Código Implementado:
  'http_only' => env('SESSION_HTTP_ONLY', true),
  'same_site' => env('SESSION_SAME_SITE', 'lax'),

Procedimiento de Prueba en Vivo (Defensa):
1. Iniciar sesión en el navegador y abrir la consola de desarrollador (F12 -> Console).
2. Escribir document.cookie y presionar Enter.
3. Demostrar que la cookie laravel_session no aparece, gracias al flag HttpOnly.

CAPÍTULO 11: V11 LÓGICA DE NEGOCIO (BUSINESS LOGIC)
--------------------------------------------------------------------------------
Control Oficial: Control V11.1.4 - Protección contra Ataques de Fuerza Bruta en Login

Vulnerabilidad y Riesgo:
La ausencia de límites de intentos permite ataques automatizados para adivinar
contraseñas mediante peticiones recurrentes.
Severidad: ALTA.

Qué se implementó:
Se implementó RateLimiter en LoginRequest que bloquea temporalmente al usuario/IP
tras 5 intentos fallidos consecutivos, disparando el evento Lockout y error HTTP 429.

Archivos, Funciones y Líneas Modificadas:
- app/Http/Requests/Auth/LoginRequest.php
  Líneas 62-78: ensureIsNotRateLimited().
- routes/api.php
  Línea 15: Ruta POST /api/login con middleware throttle:5,1.
- tests/Feature/Api/SanctumAuthenticationTest.php
  Líneas 38-55: Prueba unitaria test_api_login_is_rate_limited().

Código Implementado:
  if (! RateLimiter::tooManyAttempts($this->throttleKey(), 5)) {
      return;
  }
  event(new Lockout($this));
  $seconds = RateLimiter::availableIn($this->throttleKey());
  throw ValidationException::withMessages(['email' => trans('auth.throttle', ['seconds' => $seconds])]);

Procedimiento de Prueba en Vivo (Defensa):
1. En la pantalla de login, ingresar 5 veces contraseñas erróneas.
2. Al sexto intento, el sistema bloquea inmediatamente con el mensaje:
   "Demasiados intentos de acceso. Por favor inténtelo de nuevo en 60 segundos" (HTTP 429).

CAPÍTULO 13: V13 APIS Y SERVICIOS WEB (API AND WEB SERVICE)
--------------------------------------------------------------------------------
Control Oficial: Control V13.1.4 - Autenticación de Endpoints REST con Tokens Bearer (Sanctum)

Vulnerabilidad y Riesgo:
Exponer endpoints móviles o de GPS sin autenticación permitiría a usuarios no autorizados
consultar asignaciones o inyectar ubicaciones falsas en el sistema.
Severidad: ALTA.

Qué se implementó:
Todos los endpoints operativos móviles están agrupados bajo el middleware auth:sanctum,
requiriendo un Bearer token criptográfico emitido exclusivamente tras login válido.

Archivos, Funciones y Líneas Modificadas:
- routes/api.php
  Líneas 18-45: Grupo protegido con middleware('auth:sanctum').
- app/Http/Controllers/Api/AuthController.php
  Líneas 18-24: Emisión de token plainTextToken.
- app/Models/User.php
  Línea 21: Trait HasApiTokens.

Código Implementado:
  Route::middleware('auth:sanctum')->group(function () {
      Route::get('/me', [AuthController::class, 'me']);
      Route::get('/mis/asignaciones', [AsignacionTurnoApi::class, 'misAsignaciones']);
      Route::post('/mis/asignaciones/{id}/iniciar', [AsignacionTurnoApi::class, 'iniciar']);
  });

Procedimiento de Prueba en Vivo (Defensa):
1. Realizar una petición GET a http://127.0.0.1:8000/api/mis/asignaciones sin token.
2. El servidor responde inmediatamente con HTTP 401 Unauthorized ({"message":"Unauthenticated"}).
3. Enviar el token Bearer en la cabecera Authorization y el servidor responderá HTTP 200 OK con los datos.
