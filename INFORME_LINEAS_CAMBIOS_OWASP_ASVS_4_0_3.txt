3. V2.1.1/V2.1.2 - AUTENTICACION Y CREDENCIALES
------------------------------------------------

Descripcion:
El sistema valida las credenciales en servidor antes de permitir acceso a la
API protegida.

Riesgo:
Un login sin validacion consistente podia permitir autenticacion incorrecta,
respuestas ambiguas o acceso a endpoints sin identidad comprobada.

Que se hizo:
- El login recibe LoginRequest.
- Se ejecuta authenticate() antes de crear el token.
- Solo se utilizan datos de validated().
- Sanctum emite tokens y logout revoca el token actual.

Donde se implemento:
- app/Http/Controllers/Api/AuthController.php
  Funciones login(), me(), logout(); lineas 10-18 y 25-35.
- app/Http/Requests/Auth/LoginRequest.php
  Funciones rules() y authenticate(); lineas 24-46.
- routes/api.php
  Grupo auth:sanctum; linea 18.

Por que:
Para comprobar la identidad antes de emitir credenciales API y evitar campos
no validados.

Beneficio:
Centraliza autenticacion, reduce entradas inesperadas y protege endpoints.

Estado: implementado para login API, token Sanctum, /me y logout.

4. V2.2.1 - PROTECCION CONTRA FUERZA BRUTA
-------------------------------------------

Descripcion:
El login limita intentos repetidos y aplica bloqueo temporal.

Riesgo:
Sin limite, un atacante podia probar contrasenas repetidamente contra una
cuenta hasta encontrar una credencial valida.

Que se hizo:
- RateLimiter limita a cinco intentos.
- La clave combina email e IP.
- Se dispara Lockout al superar el limite.
- /api/login usa throttle:5,1.

Donde se implemento:
- app/Http/Requests/Auth/LoginRequest.php
  Funciones authenticate(), ensureIsNotRateLimited(), throttleKey();
  lineas 42-83.
- routes/api.php, linea 15.
- tests/Feature/Api/SanctumAuthenticationTest.php
  test_api_login_is_rate_limited(); lineas 38-55.

Por que:
Para impedir ataques automatizados contra autenticacion.

Beneficio:
Reduce la velocidad de prueba de contrasenas y devuelve HTTP 429 al superar
el limite.

Estado: implementado y probado.

5. V4.1.1 - MINIMO PRIVILEGIO Y CONTROL DE ACCESO
--------------------------------------------------

Descripcion:
Cada usuario debe recibir solo el acceso necesario para su funcion.

Riesgo:
auth:sanctum o auth solo confirmaban identidad y no impedían por si solos
que un usuario autenticado ejecutara funciones administrativas.

Que se hizo:
- Los CRUD administrativos API se agruparon bajo role:admin.
- Roles, asignacion de roles y users web requieren role:admin.
- Los endpoints moviles /mis/* mantienen auth:sanctum y control por conductor.

Donde se implemento:
- routes/api.php, lineas 22-31.
- routes/web.php, lineas 39-45.
- tests/Feature/Api/ConductorCrudTest.php
  Funciones de acceso admin y no admin; lineas 13-25 y 58-65.

Por que:
Para separar autenticacion de autorizacion y evitar que un usuario comun
administre recursos del sistema.

Beneficio:
Reduce escalada de privilegios y limita operaciones administrativas.

Estado: parcial. La frontera auditada esta protegida, pero faltan Policies
especificas y permisos por accion para todos los objetos.

6. V4.2.1 - AUTORIZACION POR OBJETO Y PREVENCION DE BOLA
---------------------------------------------------------

Descripcion:
La aplicacion verifica que el usuario puede operar exactamente sobre el
objeto solicitado, no solo sobre el endpoint.

Riesgo:
Un conductor podia cambiar el ID de una asignacion para iniciar, finalizar,
consultar o enviar GPS sobre el recorrido de otro conductor.

Que se hizo:
- iniciar() y finalizar() comparan conductor autenticado con conductor_id.
- GPS usa la comprobacion centralizada usuarioPuedeAcceder().
- Accesos ajenos devuelven HTTP 403.

Donde se implemento:
- app/Http/Controllers/Api/AsignacionTurnoApi.php
  iniciar() y finalizar(); lineas 151-196.
- app/Http/Controllers/Api/SeguimientoGpsApiController.php
  guardarUbicacion(), sincronizarLote(), estadoRecorrido() y
  usuarioPuedeAcceder(); lineas 16-86.
- tests/Feature/Api/AsignacionTurnoDriverApiTest.php, lineas 190-192.
- tests/Feature/Api/SeguimientoGpsApiTest.php, lineas 233-282.

Por que:
Para cerrar el acceso inseguro basado solamente en un ID recibido.

Beneficio:
Protege asignaciones, posiciones GPS, recorridos y paradas contra BOLA/IDOR.

Estado: parcial. Esta implementado para asignaciones y GPS; faltan Policies
para centralizar autorizacion en todos los modelos API.

7. V5.1.1 - VALIDACION COMPLETA DEL LADO SERVIDOR
--------------------------------------------------

Descripcion:
Todo dato de API, formulario o dispositivo se valida antes de persistirse o
procesarse.

Riesgo:
Coordenadas invalidas, fechas futuras, velocidades negativas, lotes excesivos
o campos no previstos podian contaminar datos operativos.

Que se hizo:
- Los CRUD API usan FormRequests y validated().
- GPS valida fechas con Carbon y limites geograficos.
- Los lotes offline tienen entre 1 y 300 ubicaciones.
- Parada web limita latitud a -90..90 y longitud a -180..180.

Donde se implemento:
- app/Http/Requests/Api/StoreUbicacionGpsRequest.php, rules(); lineas 13-39.
- app/Http/Requests/Api/SincronizarUbicacionesGpsRequest.php, rules();
  lineas 13-45.
- app/Http/Controllers/Api/InternoController.php, MicroController.php,
  ParadaController.php, PropietarioController.php, RutaController.php y
  TurnoController.php; store() y update(); lineas 14-31 normalmente.
- app/Http/Controllers/ParadaController.php; store() y update();
  lineas 39-100.

Por que:
Para rechazar datos invalidos antes del modelo, servicio o base de datos.

Beneficio:
Mejora integridad de datos, reduce errores y limita abuso de API.

Estado: implementado en los flujos auditados; debe homogeneizarse en todos
los controladores web restantes.

8. V5.3.4 - PREVENCION DE MASS ASSIGNMENT
-----------------------------------------

Descripcion:
El cliente no puede asignar campos del modelo que no forman parte de la
operacion autorizada.

Riesgo:
request->all() podia aceptar campos internos como estado, relaciones o IDs no
previstos y provocar cambios no autorizados.

Que se hizo:
- Los CRUD API usan FormRequest::validated().
- ConductorController usa only() para estado, licencia y user_id.
- ParadaController usa only() para nombre, referencia, latitud, longitud y
  estado.

Donde se implemento:
- app/Http/Controllers/Api/InternoController.php, MicroController.php,
  ParadaController.php, PropietarioController.php, RutaController.php y
  TurnoController.php; store() y update(); lineas 16-31.
- app/Http/Controllers/ConductorController.php; store() y update();
  lineas 58 y 96.
- app/Http/Controllers/ParadaController.php; store() y update();
  lineas 57 y 98.

Por que:
Para persistir solo campos expresamente permitidos.

Beneficio:
Reduce manipulacion de atributos, escalada de privilegios y corrupcion de
relaciones o estados.

Estado: implementado en los controladores auditados.

9. V13.1.1/V13.2.1 - SEGURIDAD Y LIMITES DE API
------------------------------------------------

Descripcion:
Las API deben exigir autenticacion, autorizacion, limites de consumo y
validacion de payloads.

Riesgo:
Un endpoint sin limite podia ser abusado mediante intentos de login, lotes GPS
excesivos o solicitudes repetidas. Un endpoint autenticado sin autorizacion
podia exponer datos operativos.

Que se hizo:
- Sanctum protege el grupo API.
- Login usa throttle:5,1.
- GPS usa throttle:120,1.
- Lotes GPS se limitan a 300 ubicaciones.
- Asignaciones y GPS verifican pertenencia del conductor.

Donde se implemento:
- routes/api.php; lineas 15, 18-31 y 40-44.
- app/Http/Requests/Api/SincronizarUbicacionesGpsRequest.php; linea 19.
- app/Http/Controllers/Api/SeguimientoGpsApiController.php; lineas 24-71.

Por que:
Para reducir abuso de recursos y proteger endpoints de negocio.

Beneficio:
Limita volumen, reduce superficie de ataque y protege disponibilidad y datos.

Estado: parcial. Faltan respuestas uniformes, API Resources y permisos
granulares por endpoint.

10. V4.3.1 - AUTORIZACION DE FUNCIONES ADMINISTRATIVAS
-------------------------------------------------------

Descripcion:
Las funciones administrativas deben estar separadas de las funciones comunes
y protegidas por roles o permisos apropiados.

Riesgo:
Un usuario autenticado podia acceder a CRUD de usuarios, roles, permisos o
recursos operativos sin una barrera administrativa explicita.

Que se hizo:
- Se anadieron grupos role:admin para CRUD API administrativos.
- Se anadieron grupos role:admin para roles, asignacion de roles y users web.
- Se agrego prueba de denegacion con assertForbidden().

Donde se implemento:
- routes/api.php, lineas 22-31.
- routes/web.php, lineas 39-45.
- tests/Feature/Api/ConductorCrudTest.php, linea 65.
- RolesController.php y UserController.php quedan protegidos por rutas.

Por que:
Para evitar confundir autenticacion basica con autorizacion administrativa.

Beneficio:
Impide que usuarios no administradores gestionen recursos criticos.

Estado: implementado para los grupos indicados. Policies y permisos por
accion quedan como mejora de autorizacion fina.

11. V5.3.3 - CODIFICACION DE SALIDA Y PREVENCION DE XSS
--------------------------------------------------------

Descripcion:
La salida debe codificarse segun el contexto antes de insertarse en HTML,
JavaScript o componentes de terceros.

Riesgo:
monitoreo/index.blade.php construia HTML y popups Leaflet con innerHTML usando
placas, conductores, rutas, paradas y horarios. Un valor malicioso almacenado
podia ejecutar JavaScript en el navegador del operador.

Que se hizo:
- Se agrego escapeHtml() usando textContent.
- Se aplica a valores dinamicos en renderListaUnidades(),
  renderMapaMarkers(), seleccionarUnidad() y renderControlParadas().

Donde se implemento:
- resources/views/monitoreo/index.blade.php
  escapeHtml(), linea 123; usos principales, lineas 171-216, 250-258 y
  279-306.

Por que:
Para impedir que datos de base de datos sean interpretados como HTML o
JavaScript ejecutable.

Beneficio:
Reduce XSS almacenado y XSS DOM en la interfaz de monitoreo.

Estado: implementado en la vista auditada. Otras vistas con JavaScript
 dinamico deben revisarse posteriormente.

12. V9.1.1 - COMUNICACIONES SEGURAS Y COOKIES HTTPS
----------------------------------------------------

Descripcion:
Las sesiones y credenciales deben transmitirse mediante HTTPS y las cookies
de sesion deben usar Secure en produccion.

Riesgo:
SESSION_SECURE_COOKIE podia quedar vacio. La cookie podia enviarse por HTTP
si la infraestructura no aplicaba HTTPS.

Que se hizo:
- config/session.php activa secure cuando APP_ENV es production, salvo valor
  explicito de SESSION_SECURE_COOKIE.
- .env.example declara SESSION_SECURE_COOKIE=false para Laragon local.
- Se conservaron http_only=true y same_site=lax.

Donde se implemento:
- config/session.php, linea 172.
- .env.example, linea 35.

Por que:
Para proteger cookies de sesion sin romper el entorno local HTTP.

Beneficio:
Reduce robo de sesiones por transporte no cifrado en produccion.

Estado: parcial. El servidor debe tener TLS real, APP_URL HTTPS y
APP_DEBUG=false antes del despliegue.

13. CORRECCIONES FUNCIONALES RELACIONADAS
------------------------------------------

13.1 Referencia de modelo Propietario
- Archivo: app/Http/Controllers/Api/PropietarioController.php.
- Funciones: index() y show(); lineas 13 y 25.
- Problema: llamaba a Dueño aunque el modelo importado era Propietario.
- Solucion: se uso Propietario::all() y Propietario::findOrFail($id).
- Beneficio: evita errores HTTP 500 y recupera disponibilidad del CRUD API.

13.2 Mass assignment residual en web
- Archivos: ConductorController.php y ParadaController.php.
- Problema: se utilizaba request->all().
- Solucion: se reemplazo por only() con campos permitidos.
- Beneficio: evita persistir atributos no previstos por el formulario.

13.3 Validacion de coordenadas de paradas
- Archivo: app/Http/Controllers/ParadaController.php.
- Funciones: store() y update(); lineas 39-100.
- Solucion: latitud between:-90,90 y longitud between:-180,180.
- Beneficio: evita coordenadas geograficamente imposibles.
